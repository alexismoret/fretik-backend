# @fretik/ai

Hono LLM service: chatbot (SSE resumable), vectorize, pre-extract, chat-files. The chatbot agent is a **singleton** built once at boot and reused across every request.

## Positioning

The chatbot is a **generalist B2B work assistant**, in the same vein as Claude or ChatGPT. It is **not** specialised in any industry — system prompts, tool descriptions, examples, and eval cases must stay industry-agnostic. Domain customisation comes from the field-templates layer in `@fretik/shared/templates/document-fields/` (which a team can pick to specialise their fields/document types) and from the team's own context, skills, and memory — not from this package's prompts.

When editing prompts (`src/agents/shared/agent-system-prompt.md`, `src/agents/chatbot/sub-agent-system-prompt.md`, `src/services/pre-extract/prompt.ts`, `src/services/compaction/prompt.ts`) or tool descriptions (`src/tools/*.ts`), do not introduce industry-specific vocabulary or examples. Generic business terms only: documents, entities (organizations/people), vendors, clients, contracts, invoices, reports, etc.

## Conventions

- **Agent-facing context:** every word the LLM reads (`agents/shared/agent-system-prompt.md`, `agents/chatbot/sub-agent-system-prompt.md`, `services/pre-extract/prompt.ts`, `services/compaction/prompt.ts`, every `description:` on a tool, every `.describe(...)` on a param Zod, bundled skills) follows `.agent/agent-context-framework.md` — section registry, prose rules, canonicity, cache invariants, change checklist. Load the `agent-context` skill before touching any of it. A 5-line description that does the work of 2 is a regression.
- **Managed prompts (Langfuse).** `agents/shared/agent-system-prompt.md` (unified, `<!-- AGENT:… -->` blocks resolved per agent at seed time) + `sub-agent-system-prompt.md` are the git source of truth AND the offline fallback, but at runtime the text is fetched from Langfuse Prompt Management (`lib/langfuse-prompts.ts`): prod reads label `production` (SDK-cached), dev reads `latest` (uncached). **Publishing is automatic since 2026-09-02**: the service runs `langfuse-seed-prompts` as a RELEASE TASK at boot, once per deployed `GIT_SHA` (`src/release-tasks.ts` → `backend/docs/OPERATIONS.md` §8), so editing the `.md` and deploying IS publishing — and `production` can no longer drift ahead of, or behind, the deployed code. Safe on every deploy because each prompt is diffed against the live `production` version and skipped when identical. `bun run langfuse:seed-prompts` still exists as the operator's door: bootstrapping a fresh project, or publishing an edit without waiting for a deploy. To iterate on a prompt locally WITHOUT touching `production`/prod, set `LANGFUSE_PROMPTS_LOCAL=true` in your dev `.env`: the runtime then reads the `.md` directly and publishes nothing (tracing stays on; prod keeps its current `production` version). Keep the `<!-- DYNAMIC SUFFIX -->` marker and all `{{placeholders}}` BELOW it: comments are stripped per turn and the static prefix above must stay byte-identical or the OpenRouter cache breaks. Names live in `MANAGED_PROMPTS` (`agents/shared/prompt-renderer.ts`), mirrored in the seed script.
- **A stable trace name requires an OPENED observation.** `telemetryFor("<name>")` does NOT name anything: AI SDK v7 hardcodes the span name to `invoke_agent <model>` / `chat <model>` and files the functionId under the `gen_ai.agent.name` attribute. Neither does `propagateAttributes({ traceName })` on its own — that was a v3 trace-level concept, and on a v4 server the root observation keeps its own name. Only `startActiveObservation(name, …)` names a root, so every operation that is its OWN trace goes through `withNamedTrace(name, { sessionId?, userId?, tags?, metadata? })` (`lib/trace-tool.ts`), which opens that observation AND propagates the attributes. Calls NESTED in a turn need nothing: their root already carries the name. Skipping this is not cosmetic — it merges every background operation into one indistinguishable `invoke_agent <model>` bucket (measured 2026-07-30, before the fix: 353 such roots in 3 days, 13 of the 23 names below absent from the data).
- **Trace EVERY AI call on Langfuse, with cost.** Each AI operation is a named, costed observation, differentiated by trace Name (filter in the UI) + the `environment` attribute (dev/prod). Stable names: `chatbot-turn`, `workflow-turn`, `pre-extract`, `field-suggest`, `vectorize`, `vectorize-enrichment`, `compaction`, `rag-multi-query`, `active-memory-recall`, `memory-extract`, `memory-distill`, `memory-consolidate`, `conversation-title`, `catch-up-summary`, `chat-suggestions`, `vision`, `extract`, `transform`, `embeddings`, `rerank`, `ocr`, `web-search`, `web-fetch`, `web-map`, `e2b-bash`, `e2b-python`, `agent-tool-repair`, `turn-continuation-judge`, `page-review`, `decision`. AI-SDK calls (`generateText`/`streamText`/`embed`) cost themselves through `instrumentModel`/`instrumentEmbeddingModel` (OpenRouter exact cost) — just add `telemetry: telemetryFor("<name>")` (the `@langfuse/vercel-ai-sdk` integration maps these v7 telemetry events to costed Langfuse observations; registered once in `lib/langfuse.ts`). Non-SDK calls (reranker raw fetch, Mistral OCR via Mistral SDK, E2B, the web providers) are traced manually via `startActiveObservation` / the `traceExternalCall` helper (`lib/trace-tool.ts`); E2B and the web calls carry an ESTIMATED cost (env-overridable rates `E2B_PRICE_PER_SECOND`, `PERPLEXITY_PRICE_PER_SEARCH`, `PARALLEL_PRICE_PER_*`) and are typed `generation` because Langfuse aggregates cost only on `generation`/`embedding` observations. `web-map` is the one exception with no cost line at all — it reads `robots.txt` and `sitemap.xml`, so there is no vendor to bill it. A new LLM/AI call without a telemetry name or manual observation is a regression.
- **Reading it back: v4 `events_only` moved the endpoints, it did not remove the data.** `bun run langfuse:metrics -- names [days]` (cost, calls, p50/p95 per observation name), `-- trace <id>` (one trace's generations with the reasoning/answer/cache split), `-- query '<json>'` (raw v2 Metrics). What is gone is `GET /api/public/traces`, `/traces/:id` and `/sessions`, all 404 with "not available on deployments running in Langfuse v4 events_only mode" — so `api.trace.get()` and `api.sessions.list()` throw, and any code still calling them fails silently inside a try/catch. What is NOT gone is cost: `api.observations.getMany` and `api.metrics.metrics` both work, and an observation still carries `totalCost`, `usageDetails` (`input`, `output_answer`, `output_reasoning`, `input_cache_read`), `latency`, `sessionId`, `userId` and the serving provider. **`fields` is an opt-in projection, and `core` is not "the important ones"** — it is `id`, `traceId`, `startTime`, `endTime`, `projectId`, `parentObservationId`, `type`, and nothing else. `name`, `sessionId` and `userId` live in **`basic`**; `usageDetails`/`costDetails`/`totalCost` in `usage`; `input`/`output` in `io`; `latency` in `metrics`. Passing NO `fields` returns `core,basic` — which is why a default `getMany` looks like it "came back carrying names and nothing else", and why the opposite mistake is worse: `fields=core,usage` returns every row with `name === undefined`, so a filter on the name matches nothing and the script reports an empty dataset instead of an error (cost one wrong run, 2026-09-18). Ask for every group you READ — `fields=core,basic,usage` for a cost-by-name sweep. `limit` maxes at **1000**, not 100, and the pagination key is `meta.cursor`. **And a named wrapper reports zero cost under its own name**: `withNamedTrace` opens an `agent` observation, Langfuse aggregates cost only onto `generation`/`embedding`, so `compaction` / `vectorize` / `pre-extract` all show `0.0000` in a by-`name` sweep while the `chat <model>` generations nested inside them hold the money. Group or filter by **`traceName`** to cost an operation — measured 2026-09-18, the same window gave 5 calls / $0 by `name` and 11 observations / $0.0889 by `traceName`. Verified against 4.24.0.
- **Pipeline traces get a session + a single parent.** Background/document-processing calls (OCR, pre-extract, vectorize/embeddings during indexing) run OUTSIDE a chat turn, so they'd be orphan, scattered traces. Use `withPipelineTrace(name, sessionId, …)` (`lib/trace-tool.ts`, a `withNamedTrace` with a mandatory session) — opens ONE parent `agent` trace (`pre-extract`, `vectorize`) with the AI calls nested, AND groups it under a per-subject session so the Sessions view aggregates cost: documents → `sessionId = documents:{documentId}` (shared by `runPreExtract` + `vectorizeSource` → full per-document cost; vectorize's N enrichment calls + embeddings nest under one trace instead of N roots), other vectorise sources → `{sourceType}:{sourceId}`. Background one-shots (memory dreaming, mention extraction, auto-title) use `withNamedTrace` with whatever grouping they have — `sessionId = conversationId` where one exists, `memory-dreaming:{teamId}:{date}` for a nightly batch. `withTraceSession` is only for work that JOINS an existing trace (a tool inside a turn), where opening a named observation would nest a redundant level. These traces are a historical cost record — NEVER delete them when the file/document is deleted. Embedding indexing concurrency: `AI_EMBEDDING_PARALLEL_CALLS` (default 2) × the `openrouter:embeddings` semaphore cap.
- **Tools: read `src/tools/README.md` first.** The tool convention (one file per tool, `tool()` factory, `getRuntimeContext(options)` inside `execute`, structured `{ error, code }` returns) is non-negotiable and fully documented there.
- **The web stack is three capabilities on three different backends, and `lib/web/` owns all of it.** The previous single-vendor stack was replaced on 2026-09 after two independent provider-swap benchmarks put it near the bottom (59-60% task completion against 77-80 for the leaders, at 1.6-3.2× the price): `searchWeb` → **Perplexity** `/search` (first on both boards; $5/1k flat at every depth, and a request carrying up to 5 query phrasings is ONE billing unit — which is why the tool takes `queries: string[]` and the agent no longer fires a call per reformulation), `webFetch` → **Parallel** `/v1/extract` (a server-side headless browser, so JS-rendered pages read like static ones AND the request leaves their egress, not our single datacenter IP — a hosted service reading the open web from one address collects blocks), `webMap` → **nobody**: `robots.txt` + `sitemap.xml`, free. Rules that follow from that split: availability is checked PER TOOL (`isWebToolAvailable`), never as a block; the routing policy lives in `lib/web/routing.ts` and takes its adapters as an ARGUMENT (module mocking is order-dependent here, and a sibling suite that imports the façade first links the real adapters — that is how the first version of the routing test called `api.perplexity.ai` for real); and `lib/web-egress.ts` is now LOAD-BEARING rather than defensive, because `webMap` AND the link previews fetch from this process, so `lib/web/http.ts` re-validates every redirect hop through it — by name and then by RESOLVED address, because a hostname check alone reads `169.254.169.254.nip.io` as an ordinary public domain and link previews read URLs that arrived in third-party search results. **The two search providers are not interchangeable and the fallback must not pretend they are**: Perplexity's `mode` picks a corpus (`sec` = filings) and `crawledAfter` bounds freshness, Parallel has neither, so `parallelSearch` REFUSES such a request (`WebConstraintUnsupportedError`) rather than silently answering a different question with results that look the same. Decision record, both benchmark tables and the cost model: `backend/docs/WEB-RESEARCH.md`.
- **Parallel's extract returns PROSE, and what is not prose is gone.** Measured against the live API 2026-09-12, not inferred: its Markdown carries **zero images** (Wikipedia's MacBook Pro article — dozens of photos — came back with 281 links and no `![](…)`), and on a commerce page it can keep the legal footer and drop the buy-box (apple.com/fr yielded only Cetelem financing tables, while the same URL's raw HTML holds the whole price matrix). Two consequences are permanent. Images and card metadata come from the page's own `og:` tags, read head-only by `lib/web/page-meta.ts` — the ONLY other thing this service fetches itself, hence best-effort by construction (13 of 20 sites measured; a Cloudflare refusal costs a cover image, never the answer). And a figure the extract does not show is not a figure the page lacks, which is why `webFetch`'s description tells the agent to cross-check rather than report a silence as an absence.
- **`lastCrawled` travels with every hit, and date filters are MM/DD/YYYY.** A shop or listing page publishes no date, so `publishedDate` is null on exactly the results whose freshness decides the answer — traced in production, an apple.com snapshot crawled seven weeks earlier quoted 2 999 € against a retailer's 3 559 €, both arriving undated, and the model settled it on domain authority. Perplexity exposes `last_updated`; dropping it was the bug. Its date filters (`search_after_date_filter`, `search_before_date_filter`, `last_updated_after_filter`) **reject ISO dates with a 400** — every one goes through `toUsDate`, or a date-bounded search throws and the router silently downgrades it to the fallback provider.
- **NEVER close over `ctx` at construction.** The agent is a singleton. Per-request state (`organizationId`, `conversationId`, `dynamicToolManager`, `taskManager`) is read via `getRuntimeContext(options)` inside `execute`. A closure leak silently crosses requests.
- **Mutations on `AgentRuntimeContext` must be idempotent + commutative.** Parallel tool calls can race. `dynamicToolManager.activate(names)` and `taskManager.setTasks(tasks)` already are. Any new mutable field must be too — or move state to Redis keyed by `conversationId`.
- **`prepareStep` returns explicit `{ activeTools }` every step.** Progressive Disclosure depends on recomputing the list each turn; omitting it falls back to the initial tool set and the model stops seeing newly activated tools.
- **OpenRouter models need `provider: { require_parameters: true }`.** Without it, providers that don't support `tools` silently drop the parameter and the model emits XML-looking plaintext through SSE, breaking stream parsing. Load-bearing — do not remove. Its flip side: sending a parameter the pool does NOT advertise empties the pool (HTTP 404 "No endpoints found matching your data policy") instead of dropping the field. That is why `bare` roles omit the flag (Gemini's Vertex ZDR route lacks `temperature`) and why OpenAI profiles set `provider.omitMaxTokens` (their ZDR route is Azure, which advertises `max_completion_tokens`).
- **The registry is `model_live_state`, and every profile is DERIVED from it.** There is no hand-written profile any more (22 files deleted 2026-08-30, after measurement found them staler than the rows they overrode: a curated ladder of `["xhigh","high"]` against a published `["max","high","low"]`, `cache: none` on a pair whose hosts publish a read discount). `lib/model-registry/effective.ts` builds one `ModelProfile` per row — `catalog` from what the catalogues published (`dynamicProfile`), `assessment` from what the prices and endpoints imply (cache shape, cost class, ZDR stance, `omitMaxTokens`, the vetted pool, the quantization floor). **Adding a model is a command** (`models:admin add` then `promote`), never a pull request. A missing signal answers `undefined` and NEVER `false` — "not measured" may not drive a decision. Consequences worth knowing: a database with no rows serves no models (the boot names any bound role it cannot describe and points at `models:sync`), and **any module-level `resolveModel(...)` / `getProfileForRole(...)` constant now throws at import** — resolve per call, memoised (`memoizeAgentSets`). What stays in TypeScript is `lib/model-registry/role-bindings.ts`: which model serves which internal ROLE, plus the eval evidence for it, because no API publishes that. `bun run models:admin -- audit` is offline, exits 1 on anything the engine can contradict itself about, and should run on every deploy.
- **A team picks a model per FUNCTION, not per price band.** The seven functions (`assistant`, `documents`, `memory`, `recall`, `quick-tasks`, `vision`, `pages` — `@fretik/shared/model-registry/functions`) each name a job a team can reason about; they replaced the three tiers outright, because a tier said how much a model COST, the one axis nobody could act on. `ROLE_FUNCTION` maps every `ModelRole` onto exactly one function or onto `"auto"` (every `*-fallback`, plus `page-review`) — those are never steerable, and the invariant is enforced in `tests/unit/lib/model-functions.test.ts`. Picks live in `team_ai_settings.function_profile_keys` (jsonb) and resolve through `resolveFunctionProfileKey`, which degrades to the code default on a key that is unset, unknown or no longer usable — never erroring, because a model can be retired or quarantined between the pick and the turn. What guards quality is not a frozen role list but the **eligibility engine** (`@fretik/shared/model-registry/eligibility`): measured floors per function over `CapabilitySignals`, where a missing signal answers `unknown` and NEVER `false` — automatic attribution refuses to grant on `unknown`, and an explicit team pick is never revoked by an absent measurement. Any per-request model resolution goes through `resolveModelForTeam(role, teamId)`; a module-level `resolveModel(...)` constant is a bug, since it captures the registry at import and never sees a quarantine.
- **Thinking depth resolves in three layers, and belongs to the ASSISTANT model.** The prompt bar offers no model picker — teams choose in Settings → AI models, and both chat turns and workflow runs resolve through `resolveTeamFlagship` (pin → the team's `assistant` function key → code default). What a user picks per message is the reasoning LEVEL: `handlers/chatbot.ts` takes `reasoningLevel` from the request (never persisted — a conversation can have several participants, each steering their own turns), `handlers/workflow.ts` takes it from the workflow row (a cron run has nobody there to choose), and both fall back to `team_ai_settings.flagship_reasoning_level` (the column kept its name; the TS field is `assistantReasoningLevel`), then the profile's `defaultLevel`. Every requested level MUST pass through `effectiveReasoningLevel`, which drops anything outside `selectableReasoningLevels` **and** drops the profile's own default — passing the default explicitly would route a `max-tokens` profile through the level→budget table instead of its hand-tuned `maxTokens`, changing the wire bytes of a turn nobody asked to change. Changing the team's assistant model CLEARS its stored level (`upsertTeamAiSettings`): a depth is chosen against one model's cost, latency and effort ladder. Assistant-only by design — every other function's effort is a calibrated part of its role envelope, not a preference. A profile whose ladder is absent or single-rung offers no depth choice at all, and the UI says so rather than showing a dead control.
- **Pre-turn recall is deterministic first, and the judge is the exception.** `runUnifiedRecall` gathers candidates (anchors → graph, plus three `searchRAG` arms), then `buildVerbatimBlock` selects and renders them with no LLM: score floors, per-source caps, an anchor rule that requires a lexical match to be corroborated by the semantic arm, and a positional gate that admits a document only when it tops the ranking. The recall judge runs only when the gather came back weak (`JUDGE_ESCALATION_BEST_SCORE`) — 43 % of turns, measured. `RECALL_MODE=judge` restores the old always-judge path with no deploy, but it is read at MODULE LOAD, so it takes effect on the next restart and not on the next turn; per-call, `/invoke` accepts `X-Recall-Mode` (read in the route, never the middleware, so it cannot reach `/stream`), which is the only way an A/B runs both arms against one live service instead of one restart apart. **Two suites, two different claims.** `evals:recall` scores the memory BLOCK — the right instrument for tuning the selector, and the wrong one for deciding whether to keep it. `evals:langfuse -- --suite memory-recall` scores the ANSWER over the same fixtures, because taking the judge off the critical path is a bet about what the MAIN model does with the same candidates unfiltered, and no block score settles that. **Every constant in `services/recall/verbatim.ts` is a measurement, not a preference**: the file names the eval case each one answers, and changing one without re-running `bun run evals:recall` at ten repeats is how a silent regression ships. Two traps the suite already caught and the comments record — a score that includes candidates the block cannot render makes abstention a coin flip, and enforcing the size cap by slicing the assembled string cuts a provenance marker in half, turning a citable id into one the agent calls its tools with for nothing.
- **Retrieval starts on the ROUTE, not in the turn.** `POST /stream` fires `prefetchRecallGather` as soon as it has the user's message, ahead of eleven serial round trips (saving the message, mentions, the turn log, thirty messages of history, the model resolution) that the arms then run underneath. It needs only the message text, its attachments and the session scope — `recentTail` is judge-only and assembled after the await. Anything that starts depending on the history would have to move back behind it, so keep that dependency out.
- **`<standing_memory>` is the one memory block nothing retrieves, and it is RENDERED, not generated.** It is the only surface that answers a question naming nothing ("where do we stand?"), because every other arm is query-shaped — and that gap was real: measured 2026-09-11, the two eval cases of that shape scored 3/10 and 6/10 with no block and **30/30** with this one, while spending FEWER tool calls (11.9 → 5.9 per turn on the harder one), because the control was reconstructing by hand what the block states. `services/episodes/list-standing.ts` selects it in one indexed query: team rows plus the READER's own private ones (`user_id IS NULL OR user_id = :caller`), 30 days, ≤600 tokens, newest first. `STANDING_MODE` (module-load, like `RECALL_MODE`) and per-request `X-Standing-Mode` on `/invoke` (400 on an unknown value) switch it off — `none` is a pure off switch, since the block suppresses nothing. **Per READER, not per team, and that is the load-bearing choice**: `distillConversation` writes a PRIVATE episode when a conversation has one participant, so a team-scoped artefact sees nothing a solo team's pipeline produced — measured on the real dev team, a reader sees 18 recent episodes of which 11 are private, so such an artefact misses 61 % of them. Two rules the measurement forced, both cheap to break silently: **an index never suppresses retrieval** (a one-line compression of a convention replaced the verbatim memory in `<active_memory>` and cost `mr-memory-convention` a point), and **the scaffold must say what the block is NOT for** (a condition phrased "when the message names nothing to search for" also covers a greeting; `mr-greeting` fell 10/10 → 4/10 until it read "asks for a state of play", with small talk excluded by name). A workflow gets the block in its turn-1 steering message, never in its prompt, which must stay byte-stable for a whole run — and since a run has nobody typing, what its retrieval matches on is the workflow's own name and goal (`agents/workflow/turn-one-memory.ts`, closed at 30/30 by `chain-workflow-turn-one`).
- **TRIED AND DELETED (2026-09-11): the LLM-generated team digest.** A background job wrote one prose summary per team into `team_memory_digests`, served on every turn. It was built, gated hard, measured against the deterministic renderer, and removed — so do not propose it again without reading `evals/RUNBOOK.md` first. It did not lose on quality: over 8 cases × 10 repeats it scored level (78/80 each). It lost on everything else. One LLM call per team per refresh against one indexed query; five defects in its first week that no renderer can have (an inverted link rendered as fact with a marker that resolved, so every gate passed it; a third of the sections dropped in 1 generation of 10; 16 lines lost to a wrong marker prefix; a block outliving the rows it cited by a day; the timeout hit 4 times in 10); and the scope disconnect above, which no amount of gating fixes. The generic lesson, worth more than the verdict: **a second model pass over model output is a summary of summaries.** The distiller already wrote those episode summaries and has its own eval — the value was in the writing, not in re-writing.
- **`hnsw.ef_search` and `hnsw.iterative_scan` move together, or the semantic arm loses rows in silence.** Both live in `services/search/hybrid-search.ts` with their measurements in the comments. `ef_search` decides WHICH rows come back and must stay ≥ `PER_SEARCH_LIMIT` — below it the planner will not choose a scan that cannot fill the limit, which is the whole reason the index went unused until 2026-09-10 (it was NOT the operator cost; that migration was written, measured useless, and deleted). `iterative_scan = strict_order` decides HOW MANY, and it is the half that keeps its guarantee as a corpus grows: measured, `ef=400` without it returns **67 of the 150 rows asked for**, no error, no log. Changing either is a retrieval change, so it is settled by `bun run evals:recall` at ten repeats and never by an `EXPLAIN` — and an EXPLAIN that has not asserted its own plan node is not evidence at all (`enable_seqscan=off` leaves the planner a bitmap scan plus sort, which is exact). `SEMANTIC_SCAN_MODE=exact` is the no-deploy rollback.
- **The decision model is outside the registry, on purpose.** `services/decisions/evaluate.ts` is the only caller of `experimental_evaluate`, against `openrouter.evaluationModel("typesafe/jev-1.13")` on the Decisions API (`/api/alpha/decisions`) — a different wire format from chat completions, with no reasoning ladder, no cache contract, no `require_parameters`, and nothing a team could reason about picking. Folding it into `model_live_state` would mean teaching every profile reader that a profile might describe a thing it cannot serve. Two experimental surfaces are stacked there (the SDK's `experimental_` prefix and OpenRouter's `/alpha/`), so keeping ONE call site is what makes a breaking change one file. It is traced as `decision` through `traceExternalCall`, which files it as a `generation` carrying the provider's EXACT cost — not an estimate, since the endpoint reports one. `DECISIONS_ENABLED=false` is the kill switch (module-load, like `RECALL_MODE`), and every caller falls open on it: `/internal/decisions` answers 503 and the trigger gate launches the workflow, which is the behaviour that shipped before the gate existed.
- **Two auth layers.** User-facing routes use the Better Auth cookie. Internal routes (`/internal/*`, called by API/worker) require `X-Internal-Key` + `X-Context-{Team,Organization,User,Timezone}-Id` headers via `middlewares/internal.ts`. Never mix them.
- **`E2B_API_KEY` required for the chatbot.** The `python` / `bash` tools call `@fretik/shared/services/e2b/*` which fails fast at boot if the env var is missing in production. Never log the key.
- **`AI_DB_READONLY_URL` required for the SQL tool.** `lib/db-readonly.ts` throws at boot if it's missing — it must point at the dedicated least-privilege `fretik_sql_tool` role (created by the shared `harden_sql_tool` migration), never the owner `DATABASE_URL` (the owner bypasses row-level security). Team/org scope is enforced by RLS via `set_config('fretik.team_id'|'fretik.organization_id', …, is_local=>true)` per query — the SQL no longer carries a `__TEAM_ID__` filter. Identity is reachable only through the curated `chatbot_org_members` view, never raw `user`/`member`. Operator: `ALTER ROLE fretik_sql_tool LOGIN PASSWORD '…';` then set the env.
- **Bun native I/O only.** `Bun.file` / `Bun.write` / `Bun.spawn` — never `node:fs` or `child_process`. This is enforced across the codebase.
- **Tests: read `backend/docs/OPERATIONS.md` §7 before writing one.** This package is the one with the most process boundaries, and every one of them gets a double — OpenRouter, E2B, S3, Mistral, the web providers, Langfuse. **A test that reaches a provider is not an integration test, it is a bill**: four suites embedded through the real OpenRouter until 2026-09-02, green on a laptop with a key and `401` in CI without one. Reuse what exists (`tests/lib/`: `embeddings-double`, `sandbox-fixture`, `redis-double`, `live-state-double`, `team-ai-settings-double`) before writing another, and prefer `mockModule` (spreads, keeps the real exports) over `mockModuleStrict` unless you mean to seal the module shut. The live providers are reached on purpose by `models:check -- --probe` and the evals, never by `bun test`.

## Pattern reference

- New chatbot tool → mirror `src/tools/sql-query.ts` (factory + `getRuntimeContext` + structured error return + optional `maybePersistLargeOutput` for big results).
- New HTTP endpoint → mirror `src/handlers/chatbot.ts` (middleware + fallback model try/catch + SSE resumable buffering).
- Sandbox-backed tool → mirror `src/tools/python.ts` and `src/tools/bash.ts`. Code execution is delegated to E2B via `@fretik/shared/services/e2b/run-in-sandbox` (`acquireSandbox` lazily resumes a per-conversation sandbox; `releaseSandbox` is called from the chatbot handler's `onFinish` to pause it). The conversation→sandbox mapping lives in Redis (`e2b:sandbox:{conversationId}`); no DB column. Egress is restricted by `services/e2b/network-policy.ts` (Fretik / PyPI / GitHub / common B2B service APIs only). The Python kernel is stateful for the lifetime of a conversation — context is cached in Redis (`e2b:python-ctx:{conversationId}`) and reused across `runCode` calls. Two restart granularities: `python` tool's `restart: true` → `restartPythonKernel` (kernel-only, preserves filesystem); `bash` tool's `restart: true` → `runInSandbox({ restart: true })` → `killSandbox` (nukes the whole sandbox including `/workspace`). Rich Jupyter outputs (DataFrame HTML, matplotlib plots) are captured into `RunResult.richResults` and binary representations are written under `outputs/results/{toolCallId}-{idx}.{ext}`.

## Evals (Langfuse loop)

**How to run / what to run when → `evals/RUNBOOK.md`.** One engine (`evals/`, runs the REAL chatbot — needs a live service + `AI_SERVICE_URL`, not in `.env`), Langfuse-only: `bun run evals:langfuse` runs the curated cases as a `chatbot-eval` dataset run (scored + compared in the Langfuse UI). There is no local JSON-report path. Only curated cases (`curation.ts`) run; the gold set grows from prod via `promoteTrace` (removed synthetic cases are recorded in `evals/BACKLOG.md`).

Invariants:

- **Judge is graded** (`evals/judge.ts` + `judge-rubric.md`): `correct/partial/incorrect`→1/0.5/0, model Gemini (`google/gemini-3.7-flash`, different family than the agent).
- **Curation lives in `evals/curation.ts`** (the `CURATED` map = triage gate output); only listed cases sync to the `chatbot-eval` dataset. Code is the source of truth; the dataset is a mirror that grows from prod via `promoteTrace`.
- **Failure taxonomy is DISCOVERED, never seeded** (pre-defined list = confirmation bias; score configs are non-deletable). Seed only objective configs (`correctness`/`pass-rate`/`no-error`/`latency-ok`); `failed-check` is a mechanical "which assertion broke" label. Real taxonomy comes from error analysis on prod traces.
- `scripts/*` are OUTSIDE the `tsconfig` include — `bun run typecheck` does not cover them (verify via a temp tsconfig).

## Gotchas

- Tool errors must be returned as `{ error, code }` objects, not thrown. A thrown error hides the failure from the model and surfaces as a 500 on the client. Throw only for unexpected bugs.
- Large tool outputs (>30k chars) need `maybePersistLargeOutput()` — it writes the result to a temp file and returns a `<persisted-output>` marker. Without it, the stream truncates and the model sees garbage.
- Message histories go through `prepareModelMessages()` (services/native-input) before `convertToModelMessages()`: attachments the active profile's `nativeInput` policy covers (image/video/PDF where activated) ride natively; everything else is stripped to tool-mediated (`read`/`vision`/`python`). Never bypass it — a raw history leaks file parts the provider can't resolve.
- Resumable streams spin up two ioredis connections per context. Use `maxRetriesPerRequest: null` or the subscriber gets stuck after the first failure.
